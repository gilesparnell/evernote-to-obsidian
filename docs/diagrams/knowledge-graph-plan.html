Graph — How it actually works

A visual answer to your question: "Will all my meetings live in one place?" And how a single MOC + Dataview gives you that view, plus a hundred sliced views you don't have to build by hand.

YES — AND BETTER

Every meeting → one MOC → infinite slices

Every note classified as type: meeting gets up: "[[Meetings]]" written to its frontmatter. That single field is the link that makes the note appear in the [[Meetings]] MOC's inbox automatically. Open Meetings.md → you see every meeting you've ever had, newest first.

Then Dataview goes further. The same underlying data — those frontmatter fields — can be filtered, grouped, and sorted into any view you can describe. One source of truth, many windows into it. You don't pick between "single page" and "sliced views" — you get both off the same data.

The core idea

One note. Many views.

A single classified note becomes visible from every MOC and query that matches its fields. You don't duplicate notes — you slice the same data.

The same note appears in five different views automatically. No copying, no manual indexing. The frontmatter is the index.

What your graph view looks like

Notes radiate from MOCs

The up: field creates a one-way link from every note to its parent MOC. In Obsidian's graph view this produces a radial structure where MOCs become high-connectivity hubs. Today your graph is a hairball — after classification it has shape.

What you'll be able to ask

From "show me all meetings" to anything you can describe

These are real Dataview queries you'll write against the classified data. Each one is two or three lines. None of them require manual curation.

Every meeting I've ever had, newest first
TABLE date, org, people
FROM ""
WHERE type = "meeting"
SORT date DESC

Lives inside the [[Meetings]] MOC's Organised section, or as its own dashboard. Runs over all classified notes in milliseconds.

All 1-on-1s with Jane Smith
LIST date
FROM ""
WHERE type = "meeting"
  AND contains(people, "Jane Smith")
  AND contains(tags, "1-on-1")
SORT date DESC

Goes on Jane Smith's person page. Auto-populates from the people: field on each meeting note.

STAR stories I haven't told yet
LIST
FROM ""
WHERE type = "interview"
  AND contains(tags, "star")
  AND !contains(tags, "interview-tested")

Lives in [[Interview Prep]]. The "interview-tested" tag is added manually after you use a story. The query auto-prunes.

Customer Obsession evidence — last 3 years
TABLE file.link, date, org
FROM ""
WHERE contains(tags, "aws-lp/customer-obsession")
  AND date >= date(today) - dur("3 years")
SORT date DESC

For interview prep — pulls every note tagged with the principle. Sorted by recency so the freshest stories surface first.

Meetings about a project last month
LIST
FROM ""
WHERE type = "meeting"
  AND project = "Granola Sync"
  AND date >= date(today) - dur("30 days")
SORT date DESC

Drop this on a project page. Stays current automatically.

People I've met most often at Amazon
TABLE length(rows) AS Meetings
FROM ""
WHERE type = "meeting" AND org = "Amazon"
FLATTEN people
GROUP BY people
SORT length(rows) DESC

A natural fit for the [[Amazon]] company MOC. Shows your strongest network signals there.

How classification works

Three-tier confidence-gated pipeline

For each note: rules-based scoring runs first (fast, free). If confidence ≥ 0.80, frontmatter is written. If not, Gemma 4 E4B via LM Studio gets a second pass. If still uncertain, the note goes to a review queue for you to classify by hand.

≥0.80 → atomic frontmatter write.
<0.80 → review queue.

Rules tier

Pure Python. Scans for known keywords (AWS LP terms, STAR markers, OLR vocab, org names). Extends the existing evernote-to-obsidian/scripts/classify_notes.py. No external calls — runs at full disc speed.

LM Studio tier

OpenAI-compatible local server. Function calling forces the model to emit valid R2 JSON — no parse hacks. Gemma 4 E4B (6.33 GB, full GPU offload on 16 GB Macs) handles the ~33% of notes that rules can't classify confidently.

Review queue tier

A single Markdown file: classification-review.md in the vault root. Wikilinks to each uncertain note, with proposed values and confidence. Open in Obsidian, decide, delete the row. Re-run the pipeline.

Execution order

9 units, 3 pilot stages

Claude runs the judgement-heavy units (verification, MOC design, migration safety). Codex builds the pipeline code. Each unit has its own tests; classification only starts after Unit 0.5 backs up both vaults.

Unit 0 · LM Studio verification claude
Load Gemma 4 E4B in LM Studio. Verify function calling via curl smoke test. Note model identifier.
Unit 0.5 · Vault backup claude safety net
Tarball both vaults to ~/Backups/. Verify tarball is readable before any writes.
Unit 1 · Project venv + dependencies codex
Create granolaSync/classify/ package, venv, install openai + PyYAML.
Unit 2 · Frontmatter module codex
Safe atomic read/write/is_classified. Tested with 8 unit-test scenarios.
Unit 3 · Rules classifier codex
Extended keyword sets — 15 type buckets, 4 orgs, AWS LP tag inference. Tested with realistic examples.
Unit 4 · LM Studio classifier codex
OpenAI-compatible client, function calling, schema-enforced JSON. Mocked + live smoke test.
Unit 5 · Batch pipeline CLI codex ~15h AWS run
Stage 0a: Job Hunt folder (~35 notes). Stage 0b: AWS folder. Checkpointed, resumable, iCloud-aware.
Unit 6 · Granola export schema codex
New Granola meeting notes get the full R2 schema written at export time using attendee metadata.
Unit 7 · MOC creation claude
Create 11 MOCs across both vaults. Legacy up: rewriter for existing Granola notes. Inbox smoke test.
Unit 8 · Vault migration claude irreversible
Move work notes to Business, personal notes to Personal flat. Delete empty Evernote folders.
